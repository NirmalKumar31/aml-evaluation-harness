Evaluation methodology · IBM AMLworld synthetic benchmark

Measuring a transaction-monitoring ranker under a daily review budget

This is an evaluation harness, not an AML detector. The subject is how to report a top-k metric so that it measures a ranker rather than the composition of the window it was measured on.

What these numbers are not

Every result comes from one synthetic generator. Nothing here establishes real-world AML detection performance, and no bank, customer or case validation was performed.

Alert unit
(account, calendar-day)

A transaction contributes an account-day to both endpoints; score and label are the per-day maximum.

Evaluation
under a daily budget k

A team can work a fixed number of alerts a day, so every budget metric is sensitive to how many candidates and positives that day contained.

Data
IBM AMLworld, synthetic

Published by IBM under CDLA-Sharing-1.0 and not redistributed here. No real person, account or transaction exists in it.

How the derived columns are computed
Lift
observed ÷ null_high — against the adverse end of the published band, so it is the conservative figure. Shown only where a band is published.
Random-ranker null
Read from derived/budget_null.json. It is the slot-weighted mean of daily account-day prevalence on the evaluated split, bracketed because a truncated day bounds its population rather than fixing it. It is a property of the split, not of any model.
Ceiling and efficiency
recall_ceiling@k and recall_efficiency@k are read directly from the run artifact. Efficiency is recall@k ÷ recall_ceiling@k.
Budget binds?
From nonbinding_days@k. Where the budget exceeds a day's whole account-day population, every candidate is alerted and precision equals that day's prevalence for any ranker — no ranking is being tested on those days.

The formulas, and what each one says
Random-ranker precision@k = P / N
A ranker that orders at random alerts a representative sample, so the share of its alerts that are positive is just the day's prevalence. This is why a pooled precision near the prevalence is near chance — and why a precision figure quoted without its null says very little.
Random-ranker recall@k = min(k, N) / N
A random ranker catches positives in proportion to how much of the population it reviews.
Attainable recall ceiling = min(P, k) / P
No ranker can recall more positives than there are review slots. When k < P the ceiling is below 1 and a recall that looks low may already be at the maximum.
Attainable precision ceiling = min(P, k) / min(N, k)
Every reviewed slot can be a true positive only while positives remain.
With no positives, recall is undefined
At P = 0 both random-ranker recall and the attainable recall ceiling are 0/0. The simulator reports them as undefined and plots no bar, rather than printing a rate for an empty set. Precision is different and stays defined: zero true positives out of the reviewed slots is 0, and its ceiling is 0 too, because no slot can be filled by a positive that does not exist.
The budget binds when k < N
If k ≥ N every candidate is alerted, so precision equals prevalence for any ranker and the day tests nothing about ranking. This project reports nonbinding_days@k beside every budget metric for that reason.

What this does and does not say

This spread is measured for this benchmark, this configuration and this model family. It is not a universal property of gradient boosting. The seeds vary one thing — the subsample used to estimate histogram bin edges — so the figure is a lower bound on the nondeterminism of the procedure as shipped, not an upper bound.

Architecture

Three views, kept separate because they describe three different things and conflating them has caused real errors in this project.

Two different paths, and only one produced the HI-Large result

  • The historical HI-Large image was built on the VM from a git archive of a fixed commit, uploaded to ADLS and checked against a recorded SHA-256 before the build. It was not pulled from a registry.
  • The GitHub Actions → GHCR lane is the current distribution and release path. It is tested on every push, and it is not what produced the archived result.
  • Current Bicep is not an exact reconstruction of the historical deployment. The template declares more than was created, and the OS disk deployed at a different tier.

The canonical HI-Large manifests record a commit SHA and a code tree hash and no image digest. That is source provenance, not container reproducibility.

Diagrams and technology icons are the ones committed in aml-platform/docs/architecture/, where the icon sources and licences are recorded.

Limitations

These are part of the result, not an appendix to it. The full treatment is in LIMITATIONS.md.

  • One synthetic generator

    Every finding is scoped to IBM AMLworld. Nothing transfers to real AML operations.

  • No bank, customer or case validation

    No operational review, no alert disposition data, no feedback from an investigator.

  • Not a production detector

    This is a research harness. It has no deployment that serves traffic and makes no claim about detection quality in production.

  • Raw data and replay bundles are not distributed

    AMLworld is CDLA-Sharing-1.0 and is obtained from its own source. The row-level replay bundles are withheld while their redistribution status is unreviewed, so tests that need them skip by name.

  • Provenance verifies lineage, not correctness of an estimand

    The gate answers "did this number come from that code and that data". It cannot answer "is this number measuring the thing the sentence says it measures". A ring-recall lift was traceable, recomputable and wrong by a sign; only a negative control caught it.

  • The split is label-aware, and the ring filter is not neutral

    The cut was informed by ring-retention diagnostics, so it is a design choice rather than an external protocol. Rings are dropped because they reuse accounts, so the surviving population is systematically larger and every ring_recall level is inflated by composition.

  • The per-typology result is exploratory

    Post hoc and lineage-limited. The ordering does not transfer between rungs, and the size of any per-structure spread is not established on this benchmark.
