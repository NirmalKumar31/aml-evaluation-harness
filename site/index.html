Measuring a transaction-monitoring ranker under a daily review budget

An alert is one account on one calendar day, and a review team can open only so many of them before the day ends. This project measures what a ranker is actually worth under that constraint: against the random-ranker null for the same window, across seeds, at three dataset scales — with every number on this site traceable to the committed artifact it was read from.

The measurement problem, in three minutes

Transaction-monitoring results are usually quoted as a single number on a single run. Almost every part of that sentence hides a decision.

The unit matters: this harness scores an account-day, and takes the maximum score and the maximum label within the day, because that is the object a reviewer actually opens. The budget matters: at k=50 the same model is graded on a different quantity than at k=1000. The window matters: on the evaluated HI-Medium split there are 12 thin days from 2022-09-17 on which nearly every surviving account-day is a positive, so a uniformly random ranker already reaches precision@50 of 0.45392–0.49147. And the seed matters: eight seeds of one configuration move precision@50 by 37.19% of its own mean.

So the deliverable here is not a detector. It is the apparatus that makes a claim checkable — alert units, budgets, nulls, ceilings, stability, a lineage registry that records which runs are canonical, a register of every value that was withdrawn, and a publication gate that refuses to let a document quote a number the artifacts no longer support.

What these numbers are not

They come from one synthetic generator. There is no bank, no customer outcome and no investigator feedback anywhere in this repository, so nothing here is evidence about detection in production, and no result should be read as a benchmark ranking of one learner against another.

Three findings

Each one is a picture first, with what it licenses and what it does not written underneath it.

Finding 1

The same ranker is strong or ordinary depending on the day it is scored on

On the evaluated HI-Medium split a uniformly random ranker already attains precision@50 of 0.45392-0.49147 pooled, because the window has 12 thin days from 2022-09-17 on which almost every account-day is a positive. A level quoted without that band is unreadable.

What the picture shows. Each observed precision@k next to the random-ranker band for the same budget on the same split. The gap, not the level, is the result.

What it does not license. The band is a property of the SPLIT, not of any model, so it does not transfer to another window, another rung or a production portfolio. The logistic level shown here is a withdrawn figure that the registry permits only in this qualified form: beside its null.

Finding 2

One seed is not a result: precision@50 spans 37.19% of its own mean

8 seeds of the same GBDT configuration on HI-Medium, changing nothing but the seed. precision@50 runs from 0.59144 to 0.89815 around a mean of 0.8248.

What the picture shows. Every seed as its own point, with the mean and the full observed range. A single-seed headline could have landed anywhere in this span.

What it does not license. Eight seeds bound what was observed; they are not a confidence interval, and the range is not an error bar. Nothing here separates seed sensitivity from the split's own thin-day structure.

Finding 3

Scale changes what the metric can reach, and this is not a model comparison

recall@200 on the canonical HI-Medium run against the three HI-Large cloud seeds. The rungs differ in learner, in split, in window and in the number of account-days competing for the same 200 daily slots.

What the picture shows. Two rungs side by side at one budget, each point linked to the manifest it was read from.

What it does not license. NOT a comparison of GBDT against LightGBM. Only LightGBM was run at HI-Large: scikit-learn gradient boosting needed a 33.5 GB training matrix against LightGBM's 14.9 GB on a roughly 31 GB machine, so it did not complete. That is a memory measurement. It says nothing about how either learner would have scored.

The delivery path is part of the result

A number is only reproducible if the thing that produced it can be named exactly. The current lane below builds one image, tests inside it, scans it, publishes it by digest and deploys this website from the exact artifact that passed.

  1. Git commit
  2. Pull request
  3. Unit, reproducibility and publication gates
  4. Docker build
  5. Suite runs inside that image
  6. Trivy and pip-audit
  7. CodeQL
  8. GHCR commit digest
  9. Signed release tag
  10. Byte-identical manifest promotion
  11. GitHub Release
  12. GitHub Pages deployment

The HI-Large result did not come from that lane. It was produced once on Azure from a verified source archive, in a container built on the machine itself — so it has source provenance but not container reproducibility, and the two paths are kept apart everywhere on this site.

Four limitations that bound everything above

  1. One synthetic generator

    All data comes from IBM AMLworld. Its laundering patterns are generated by rules, so a model can learn the generator rather than the behaviour, and no result here transfers to a real portfolio.

  2. No bank, customer or case validation

    There is no investigator outcome, no confirmed SAR and no false positive cost anywhere in the pipeline. “Precision” here means the share of alerted account-days carrying a synthetic label.

  3. The split is label-aware, and the ring filter is not neutral

    Test days are chosen with knowledge of ring membership so that rings are not torn across the boundary. That protects against one leak and introduces a selection effect of its own, which the split-inflation work measures rather than assumes away.

  4. Provenance verifies lineage, not correctness

    The gates prove that a published number came from the artifact it claims, produced by the code it names. They cannot prove that the estimand was the right one to measure.

The full limitations list, the lineage registry and the withdrawal register are on the engineering page.
