AML model evaluation under real review limits

A model can rank millions of transactions. Investigators can review only a few alerts.

This project evaluates transaction-monitoring models under that constraint. It measures which suspicious account-days reach a fixed daily review queue, how much the answer moves across data windows and random seeds, and whether apparent performance survives leakage and provenance checks.

Why ordinary model scores are not enough

A bank can score millions of transactions. An investigation team can open only a fixed number of alerts a day, so a model can look strong on an aggregate metric and add little inside the queue people actually work.

The unit is what most summaries skip. This project scores an account-day — one account on one calendar day — because that is what a reviewer opens. Rank them, take the day's top k, and the question is concrete: of the alerts someone actually reads, how many were worth reading?

Three things then move the headline without the model changing at all: how many suspicious account-days the day holds, where the split is drawn, and which seed the run used.

An evaluation harness built around the decision that matters

The deliverable is not a detector. It is a reproducible evaluation system that measures a ranker the way a review team would meet it, and refuses to publish a number it cannot trace.

  1. 1Data and temporal splitaccount-days, a cut date, rings kept whole
  2. 2Model trainingthe families that fit, at a fixed row order
  3. 3Daily top-k evaluationrank the day, score the k alerts
  4. 4Seed and leakage stress testsrerun, permute, re-split
  5. 5Verified artifact and publicationevery value linked, gate-checked
  • Time-aware splits that keep laundering rings whole across the cut.
  • A linear baseline beside tree models, so the gain over something simple stays visible.
  • Precision, recall and attainable recall at daily budgets, each compared with what a random ranker scores on the same window.
  • Reruns across seeds, with leakage controls injected and permuted rather than assumed away.
  • Every published value linked to its artifact and generator.

What the evaluation changed

Three results, each with its number and its boundary.

Finding 1

Change how the test set is drawn and the metrics disagree

“Performance improved” is not a statement this data supports on its own; it depends which metric you read.

Two temporal protocols on HI-Small, same cut date, 5 seeds each. The naive one readmits 966 positive transactions whose rings were already seen in training. Average precision then reads 40.0% higher, recall at a 50-alert budget 4.1% lower.

Boundary. A preregistered sensitivity analysis on HI-Small, not evidence of leakage: part of the move comes from the naive split's higher prevalence, and nothing here claims the effect holds on another dataset.

Finding 2

One seed is not a result: precision@50 spans 37.19% of its own mean

A decision taken from one run could rest mostly on which seed that run used.

8 seeds of one GBDT configuration on HI-Medium, changing nothing but the seed. precision@50 runs 0.59144 to 0.89815, a span worth 37.19% of the mean.

Boundary. Eight seeds bound what was observed rather than estimate a distribution, so the range is not a confidence interval.

Finding 3

The same protocol ran at 179.7M transactions

Scale did not need a different method, which is what makes the smaller rungs comparable to this one.

The top rung of AMLworld is 179,702,229 transactions. The evaluation ran there on one 31 GB machine, three seeds, at a fixed training row order, under the same units, budgets and publication gate as the smaller rungs.

Boundary. Not a comparison of learners: scikit-learn gradient boosting needed a 33.5 GB training matrix against LightGBM's 14.9 GB on the roughly 31 GB machine and did not complete, which is a memory measurement and says nothing about how either learner would have scored.

What this is useful for

It is aimed at decisions a team makes before anything ships.

  • Choosing a model against the review capacity a team really has.
  • Separating model signal from prevalence, seed and split effects.
  • Finding evaluation leakage while it is still cheap to find.
  • Comparing runs whose inputs, code and artifacts are traceable.
  • Reporting uncertainty openly instead of behind one number.

Nothing here was measured against real customers, investigator outcomes or losses, so no claim about detecting financial crime in production follows from it.

How to use it

Start with the findings above, then the results explorer, then engineering & MLOps for the cloud run, CI and release controls.

Where this does not fit

An evaluation and research harness on the synthetic IBM AMLworld dataset — not a live monitoring service, an investigation interface or a validated banking model. The review queue is modelled; no investigator ever worked one of these alerts.

How the evidence was produced

  1. Build temporal, ring-aware evaluation windows.
  2. Train the families supported at each scale: a logistic-regression baseline and scikit-learn gradient boosting on HI-Medium, LightGBM on HI-Large.
  3. Rank account-days and evaluate the top k alerts per day.
  4. Repeat across seeds and compare against the null for that window.
  5. Run leakage, split and provenance checks.
  6. Publish only artifact-backed values, through automated gates.

568 automated checks run on the current tree, and the gate re-reads 706 published values against the artifacts on every run.

Four limitations that bound everything above

  1. One synthetic generator

    AMLworld's laundering patterns are produced by rules, so a model can learn the generator rather than the behaviour.

  2. No bank, customer or case validation

    No investigator outcome and no false-positive cost exists here; precision means the share of alerted account-days carrying a synthetic label.

  3. The split is label-aware

    Test days are chosen knowing ring membership, which removes one leak and introduces a selection effect that Finding 1 measures.

  4. Provenance verifies lineage, not correctness

    The gates prove a number came from the artifact and code it names, not that the quantity was the right one to measure.

The full list, the lineage registry and the register of withdrawn values are on the engineering page.
