Engineering & MLOps

How a number gets from a machine to a published claim

Two delivery paths exist in this project and they are not the same path. One is the current CI and release lane, which builds a single image, tests inside it, scans it, publishes it by digest and deploys this website from the exact artifact that passed. The other is the historical Azure run that produced the HI-Large result once, from a verified source archive, in a container built on the machine itself. They are kept apart here because conflating them would claim a reproducibility the second one does not have.

Two lanes

Current

CI, release and deployment — how the software ships today

Every step below runs on every pull request to the protected branch, and the merge is blocked until all of them pass.

  1. 1 Git commit Signed with an SSH key; the signature is checked on the branch.
  2. 2 Pull request Branch protection requires every check below to pass before merge.
  3. 3 Unit, reproducibility and publication gates 539 tests on the current tree. The publication gate re-reads 706 published values against the artifacts and must report zero findings.
  4. 4 Docker build One image, built once from a hash-pinned requirements lock.
  5. 5 Suite runs inside that image The image that is tested is the image that is published. Nothing is rebuilt afterwards.
  6. 6 Trivy and pip-audit The built image and the locked dependency set are both scanned.
  7. 7 CodeQL Static analysis of the Python surface, with triage recorded.
  8. 8 GHCR commit digest Pushed and pulled by immutable digest, never by a floating tag.
  9. 9 Signed release tag The tag is signed and the commit it points at is GitHub-verified.
  10. 10 Byte-identical manifest promotion A release tag is created by copying the tested manifest bytes. No second build can differ from the one that passed.
  11. 11 GitHub Release The notes carry the digest, so a reader can pull exactly what was tested.
  12. 12 GitHub Pages deployment The deploy job publishes the artifact the site-build job uploaded, and has no source tree to rebuild from.
  • Every action is pinned to a commit SHA, not a moving tag.
  • Branch protection requires test, static, public-surface, build, analyze python, pip-audit on the locked set and site-build.
  • The image the suite runs inside is the image that is pushed. A release never rebuilds it.
  • Promotion to a release tag copies identical manifest bytes, so the tagged image is the tested image by construction.
  • The release commit and its tag are signed, and the merge commit is GitHub-verified.
  • The container is pullable by immutable digest.
  • The Pages deploy job publishes the artifact site-build uploaded and has no source tree to rebuild from.

Historical

Recorded Azure execution — how the HI-Large result was produced, once

This lane ran in the past, on a machine that no longer exists. It is documented rather than repeatable, and nothing on this site claims otherwise.

  1. 1 Fixed source commit One commit id, recorded in every manifest the run produced.
  2. 2 git archive A source archive was shipped. No container image was shipped.
  3. 3 SHA-256 verification The archive digest was checked after upload and again on the machine.
  4. 4 ADLS Gen2 Shared-key access disabled; the account was reachable by identity only.
  5. 5 Managed identity No service principal was created and no secret was issued or stored.
  6. 6 Azure virtual machine Four vCPUs and roughly 31 GB. The quota could not be raised, which is why three HI-Large seeds were bought rather than eight.
  7. 7 Container built on the VM Built there, from the verified source archive. It was NOT pulled from GHCR, so the exact image cannot be reconstructed by digest.
  8. 8 DuckDB and LightGBM execution About 26 minutes and 30 of 31 GB resident per fit. scikit-learn gradient boosting needed 33.5 GB and did not complete.
  9. 9 Result manifests Written back to storage and then into the committed archive.
  10. 10 Publication gate The same gate the current lane runs; the HI-Large numbers on this site passed it.
  • The HI-Large image was not pulled from GHCR. It was built on the virtual machine from the verified source archive.
  • The Bicep templates in the repository are a current, reviewed deployment — not an exact reconstruction of the machine that ran the job.
  • What this lane establishes is source provenance: a fixed commit, a checksummed archive, and manifests that name both. It does not establish container reproducibility.
  • No service principal was created, no secret was issued, and shared-key access to storage was disabled.

The scientific gates

CI in this project does not only ask whether the code runs. It asks whether the documents still say what the artifacts support.

The publication gate

Every number in a published document carries a marker naming the artifact and field it came from. The gate re-reads 706 of them against the artifacts on every run and fails on any disagreement. 77 are exempted, and each exemption is explicit rather than implied.

The retraction registry

33 withdrawn claims are recorded with what replaced them and why. 33 patterns run against every candidate string, so a retracted value cannot quietly return to a document.

Frozen provenance

Derived artifacts record the git object id of the package tree they were produced from — currently f8d4a113edb4 — and the generator script that produced them. Editing the package invalidates the artifacts that name it, which is the point.

Lineage registry

Every result set is registered as canonical, supporting or superseded. This website refuses to build if it is asked to display a value from a superseded lineage, or from a lineage that is not registered at all.

Reproducibility, in three honest tiers

What each tier needs, and what it establishes.

Full replay is not available from this repository

The 9 row-level replay bundles — 45 Parquet files, 526,355 rows — are held privately while their CDLA redistribution status is unreviewed. row_level_data_included is false in the published inventory. Tests that need them skip, by name, with the reason printed. To run the full replay tier you obtain AMLworld from its own source and regenerate the bundles.

Pulling the tested image

The container is published to GitHub Container Registry and is pullable by immutable digest. The digest for a release is printed in that release’s notes, and a release tag is created by copying the tested manifest bytes rather than by building again.

docker pull ghcr.io/nirmalkumar31/aml-evaluation-harness@sha256:<digest from the release notes>

Limitations

  1. One synthetic generator

    All data comes from IBM AMLworld. Its laundering patterns are generated by rules, so a model can learn the generator rather than the behaviour.

  2. No bank, customer or case validation

    No investigator outcome, no confirmed SAR, no false-positive cost. “Precision” means the share of alerted account-days carrying a synthetic label.

  3. Not a production detector

    There is no deployment, no threshold policy, no case management and no model risk documentation. The deliverable is the measurement apparatus.

  4. Raw data and replay bundles are not distributed

    The aggregate artifacts are published; the row-level material is not, for the licensing reason stated above.

  5. Provenance verifies lineage, not the correctness of an estimand

    The gates prove a number came from the artifact it names, produced by the code it names. They cannot prove the quantity was the right one to measure.

  6. The split is label-aware, and the ring filter is not neutral

    Test days are selected with knowledge of ring membership so rings are not torn across the boundary. That removes one leak and introduces a selection effect, which the split-inflation work measures rather than assumes away.

  7. The per-typology result is exploratory

    Typology counts in the evaluated window are small, and no multiplicity correction is applied.

  8. The HI-Large lane is documented, not repeatable

    Source provenance without container reproducibility, for the reason set out in the historical lane above.
